AI에게 프로그램을 만들어 달라고 하면 코드와 설명을 받을 수 있습니다. 그렇다면 굳이 문법을 배우고, 오류를 직접 고치는 연습까지 해야 할까요? 우선 작은 검색 기능을 예로 들어 살펴보겠습니다. 이 수업에서 확인할 것은 코드를 얼마나 많이 작성할 수 있는지가 아니라, 제안받은 코드가 원하는 조건에 맞게 동작하는지 판단할 수 있는가입니다.

프로그래밍 경험이나 AI 서비스 계정은 없어도 됩니다. 이번 수업에서는 코드를 실행하기보다 주어진 상황을 읽고 판단하는 과정을 연습합니다. 개발 도구를 설치하고 프로그램을 실행하는 과정은 다음 수업에서 다루겠습니다.

이 수업을 마치면

  • AI에게 맡길 수 있는 초안 작성과 개발자가 정해야 할 요구사항·검증을 구분할 수 있습니다.

  • 결과가 한 번 맞았다는 사실만으로 충분하지 않은 이유와 추가 확인 방법을 설명할 수 있습니다.

  • 자신의 프로젝트에서 C++을 배우려는 이유를 구체적인 제약과 연결할 수 있습니다.

1 작동하는 화면 뒤에 남은 질문

우선 게임의 아이템 목록에서 이름을 검색하는 기능을 만든다고 가정하겠습니다. 아래 내용은 설명을 위해 새로 작성한 가상 사례이며, 특정 AI 서비스의 실제 답변이나 측정 결과는 아닙니다.

개발자가 AI에게 “아이템 이름을 검색하는 기능을 만들어 줘”라고 요청했습니다. 받은 초안에 아이템 세 개를 넣었더니 원하는 이름이 화면에 나타났습니다. 그렇다면 이 기능은 제대로 완성되었다고 볼 수 있을까요?

현재 확인한 것은 “입력한 자료와 검색어에서는 기대한 결과가 나왔다”는 사실입니다. 다만 다음과 같은 조건은 아직 확인하지 않았습니다.

  • 이름 전체가 같아야 찾은 것으로 볼까요, 일부만 같아도 될까요?

  • 같은 이름의 아이템이 여러 개면 모두 보여 줄까요?

  • 목록이 비어 있거나 검색 결과가 없으면 무엇을 보여 줄까요?

  • 자료가 많아져도 화면 조작에 지장을 주지 않을까요?

앞의 세 질문은 기능이 어떻게 동작해야 하는지 정하는 문제이고, 마지막 질문은 주어진 환경에서 실행 비용을 확인하는 문제입니다. “검색해 줘”라는 요청만으로는 이 조건들이 정해지지 않습니다. AI가 빈 부분을 채웠더라도, 그 조건이 개발자가 의도한 것과 같은지는 별도로 확인해야 합니다.

잠깐 예측해 보기

목록이 [나무검, 강철검, 회복약]이고 검색어가 “검”이라면, 결과는 몇 개여야 할까요?

이 경우에는 먼저 검색 규칙을 정해야 합니다. 이름의 일부가 일치하면 찾은 것으로 본다면 두 개이고, 이름 전체가 같은 항목만 찾는다면 결과는 없습니다. 즉, 코드가 맞는지 판단하려면 어떤 동작을 원하는지부터 분명하게 정해야 한다는 뜻입니다.

2 코드 제안을 검토하는 네 단계

다음으로 AI가 제안한 코드를 검토하는 과정입니다. AI는 설명의 초안을 작성하거나, 구현 방법과 테스트할 상황을 생각하는 데 활용할 수 있습니다. 다만 생성된 코드에도 오류나 보안 문제가 있을 수 있으므로 직접 검토하고 테스트해야 합니다. GitHub의 Copilot 공식 안내에서도 이 점을 설명하고 있습니다. 제안받은 코드가 있다는 사실만으로 구현과 검증이 끝났다고 판단해서는 안 됩니다. [참고 1]

이 강좌에서는 다음과 같은 순서로 확인하겠습니다.

원하는 동작을 적기 → 실행 결과를 예상하기 → 직접 확인하기 → 예상과 다르면 원인을 좁히기

앞의 검색 기능에 이 순서를 적용하면 다음과 같습니다.

  1. “이름 일부가 일치하는 모든 항목을 보여 준다. 결과가 없으면 빈 목록을 보여 준다”라고 규칙을 정합니다.

  2. 작은 목록과 검색어를 고르고, 나와야 할 결과를 실행 전에 적습니다.

  3. 나중에 구현을 실행해 실제 결과와 비교합니다. 지연이 문제라면 사용할 기기와 자료 규모를 정해 시간도 측정합니다.

  4. 결과가 다르면 요구사항이 모호했는지, 코드가 규칙과 다르게 동작하는지, 테스트에 사용한 자료가 잘못되었는지 구분합니다.

AI에게 같은 질문을 다시 했을 때 같은 답을 받더라도, 그것이 실제 실행 결과를 대신하지는 않습니다. AI가 작성한 테스트도 마찬가지입니다. 구현과 테스트가 같은 잘못된 가정을 바탕으로 작성될 수 있으므로, 기대 결과 자체가 맞는지도 확인해야 합니다.

여기서 빌드 성공과 기능 검증도 구분할 필요가 있습니다. 컴파일은 C++ 소스 코드를 번역하는 과정이며, 빌드에는 보통 컴파일과 필요한 부분을 연결하는 과정이 포함됩니다. 빌드가 성공했다는 것은 중요한 확인 사항입니다. 하지만 검색 결과를 모두 보여 주어야 하는데 첫 항목만 보여 주는 코드도 문법적으로는 올바를 수 있습니다. 따라서 빌드가 성공했더라도 요구사항대로 동작하는지는 따로 확인해야 합니다.

3 그중에서 왜 C++인가

앞에서 설명한 검토 과정은 다른 언어를 사용할 때도 필요합니다. 그렇다면 그중에서 C++을 배워야 하는 이유는 무엇일까요? 만들려는 프로그램에서 어떤 부분을 직접 이해하고 제어해야 하는지에 따라 판단할 수 있습니다. 이 강좌에서는 다음 세 가지를 중심으로 기초를 다루겠습니다.

데이터 처리 비용을 설명하고 싶을 때

우선 데이터 처리 비용입니다. 아이템 검색 결과가 정확하더라도, 자료가 많아지면 처리 시간이 길어질 수 있습니다. 데이터를 어떤 형태로 보관하는지, 목록을 몇 번 순회하는지, 중간 결과를 얼마나 복사하는지 등이 비용에 영향을 줍니다. C++에서는 값의 복사와 이동, 표준 컨테이너와 알고리즘을 배우면서 이러한 선택이 코드에 어떻게 나타나는지 살펴볼 수 있습니다.

다만 C++로 작성했다고 해서 무조건 빠른 것은 아닙니다. 입력 규모, 알고리즘, 구현 방식, 빌드 설정과 실행 환경에 따라 결과가 달라집니다. 따라서 이 강좌에서는 빠를 것이라는 추측보다 조건을 맞춘 측정 결과를 기준으로 판단하겠습니다. C++ Core Guidelines에서도 성능을 판단할 때 측정할 것을 강조합니다. [참고 2]

자원을 언제까지 유지할지 정하고 싶을 때

다음으로 자원의 수명입니다. 프로그램은 메모리뿐 아니라 열린 파일과 같은 자원도 사용합니다. 필요한 동안에는 자원을 유지하고, 사용이 끝나면 정리해야 합니다. 사용이 끝난 데이터를 계속 유지하면 낭비가 생길 수 있고, 아직 필요한 자원을 먼저 정리하면 잘못된 접근이 발생할 수 있습니다.

C++에서는 자원 관리를 객체의 수명과 연결하는 방식을 사용할 수 있습니다. 이 방식을 RAII라고 부릅니다. 지금은 약어를 외우기보다 “관리 객체가 소멸할 때 그 객체가 맡은 자원도 정리되도록 구성한다”는 의미로 이해하면 됩니다. 파일 관리 객체나 스마트 포인터가 어떻게 이 역할을 하는지는 이후 수업에서 설명하겠습니다. [참고 3]

모든 자원을 직접 해제하는 코드를 작성하자는 의미는 아닙니다. 검증된 관리 도구를 활용하되, 그 도구가 어디까지 보장하는지 이해하는 것이 중요합니다. 관리 도구를 사용하더라도 다른 곳에 남아 있는 모든 참조의 안전성까지 자동으로 보장되지는 않습니다.

기존 네이티브 코드와 함께 일하고 싶을 때

마지막으로 기존 네이티브 코드와의 연결입니다. 사용할 엔진이나 라이브러리가 C++ 인터페이스를 제공한다면, 우선 함수의 인자와 반환값을 읽을 수 있어야 합니다. 이때 함수가 데이터를 복사해서 보관하는지, 잠시 빌려 쓰는지, 실패했을 때 어떤 방식으로 알리는지 등을 확인해야 연결 코드를 올바르게 작성할 수 있습니다.

예를 들어 Windows에서 Direct3D 12를 직접 사용하려면 제공되는 네이티브 인터페이스와 자원 관리 규칙을 이해해야 합니다. 이 강좌에서는 그래픽 API를 바로 다루기보다, 관련 문서를 읽는 데 필요한 타입, 함수, 수명과 오류 처리의 기초부터 설명하겠습니다. [참고 4]

물론 목적에 따라 다른 언어와 도구가 더 적합할 수도 있습니다. 잠깐 사용할 문서 정리 도구를 만들고, C++ 연동이나 세밀한 자원 제어가 필요하지 않다면 더 적은 준비로 목적을 달성하는 방법을 선택할 수 있습니다. C++을 배우는 이유도 이러한 조건을 기준으로 판단하면 됩니다.

4 AI를 학습에 활용하는 방법

이어서 AI를 학습에 활용하는 방법입니다. 처음부터 완성된 프로그램 전체를 받아 보면 아직 모르는 개념이 한꺼번에 등장할 수 있습니다. 따라서 지금 배우는 범위 안에서 질문을 나누어 보는 것이 좋습니다.

  • 설명 요청: “이 부분이 처리하는 입력과 만드는 결과를 설명해 줘. 아직 배우지 않은 용어는 풀어서 써 줘.”

  • 검토 요청: “내가 적은 요구사항에서 빠진 경우를 찾아 줘. 정답 코드는 아직 보여 주지 마.”

  • 비교 요청: “두 구현이 같은 결과를 내려면 어떤 전제가 필요한지 알려 줘.”

위 질문은 학습을 위해 새로 작성한 예시이며, 특정 모델에서 원하는 답변을 보장하지는 않습니다. 답변을 받았다면 수업의 설명과 공식 문서를 대조하고, 실행할 수 있는 내용은 직접 확인해야 합니다. 또한 회사 코드나 비공개 자료를 외부 AI 서비스에 입력하기 전에는 자료를 전송할 권한과 해당 서비스의 데이터 처리 조건을 먼저 확인해야 합니다.

그렇다면 실제로 이해했는지는 어떻게 확인할 수 있을까요? 조건 하나를 바꾸었을 때 결과를 예상할 수 있는지, 잘못된 결과를 재현할 입력을 만들 수 있는지, 아직 모르는 부분을 구체적으로 설명할 수 있는지를 확인하면 됩니다.

AI를 사용하지 않아도 같은 방식으로 공부할 수 있습니다. 도구의 사용 여부와 관계없이, 판단할 수 있는 근거를 남기는 것이 중요합니다.

5 직접 작성하는 네 줄 검토 메모

이제 가상 검색 기능의 규칙을 정하겠습니다. 아이템 이름에 검색어가 포함되면 일치한 것으로 보고, 일치한 모든 항목을 원래 순서대로 반환합니다. 일치한 항목이 없으면 빈 목록을 반환합니다. 검색어는 비어 있지 않다고 가정합니다.

이제 다음 네 항목을 직접 작성해 보겠습니다. 아직 코드를 작성할 필요는 없습니다.

  1. 원하는 동작은 무엇인가

  2. 현재 확인한 사실과 아직 모르는 것은 무엇인가

  3. 추가로 확인할 입력과 기대 결과는 무엇인가

  4. 채택 여부를 판단하려면 어떤 증거가 더 필요한가

아래 연습문제의 해설을 읽기 전에 먼저 자신의 답을 작성해 보세요.

6 연습문제

연습 1 작은 입력에서도 빠진 조건 찾기

목록은 [나무검, 강철검, 회복약]이고, 검색어는 “검”입니다. 초안은 [나무검]을 결과로 반환했습니다. 5절에서 정한 규칙에 따라 이 결과를 채택할 수 있을까요? 판단한 이유와 추가로 확인할 부분을 작성해 보세요.

연습 2 빈 목록을 예상하기

목록은 비어 있고 검색어는 “검”입니다. 5절의 규칙에 따른 기대 결과를 작성해 보세요. 실제 프로그램이 오류로 종료했다면, AI에게 다시 만들어 달라고 요청하기 전에 어떤 내용을 기록해야 할까요?

연습 3 빠르다는 판단을 보류하기

개발자가 “아이템 세 개에서는 즉시 표시되었으니 큰 목록에서도 충분히 빠르다”고 판단했습니다. 아직 확인하지 못한 점 두 가지와 성능을 판단하기 전에 정해야 할 조건 두 가지를 작성해 보세요. 측정하지 않은 실행 시간을 임의의 숫자로 적지는 않습니다.

연습 4 내 학습 이유 만들기

만들고 싶은 프로그램을 하나 정하고 다음 문장을 완성해 보세요.

“나는 ___을 만들고 싶다. 특히 ___이라는 제약을 이해해야 한다. 그래서 C++에서 ___을 배우려 한다.”

현재 목적에는 다른 언어가 더 적합하다고 판단해도 괜찮습니다. 그 경우에는 C++을 배우려는 별도의 이유가 있는지, 지금 필요한 학습인지 구분해 보면 됩니다.

7 해설과 스스로 확인할 기준

연습 1 해설

이 결과는 채택할 수 없습니다. 기대 결과는 [나무검, 강철검]인데, 일치하는 항목 중 강철검이 빠져 있기 때문입니다. 이후 코드를 읽을 수 있게 되면 첫 번째 일치를 찾은 직후 탐색을 끝내는지 등을 확인할 수 있습니다. 다만 지금은 코드를 확인하지 않았으므로 이것을 실제 원인이라고 단정할 수는 없습니다. 우선 기대 결과와 실제 결과가 다르다는 사실을 재현할 수 있도록 기록하면 됩니다.

연습 2 해설

기대 결과는 빈 목록입니다. 프로그램이 오류로 종료했다면 사용한 입력, 기대 결과, 실제로 발생한 현상과 재현 순서를 기록합니다. 빈 목록에서 존재하지 않는 항목에 접근했을 가능성은 조사할 대상이지만, 코드와 오류 정보를 확인하기 전에는 원인으로 확정할 수 없습니다. 기대 결과를 먼저 정하고 확인한 사실과 추측을 구분했다면 이 연습의 목표를 충족한 것입니다.

연습 3 해설

예를 들어 실제로 처리할 최대 자료 수와 허용할 수 있는 응답 시간을 아직 모릅니다. 측정 전에는 사용할 기기, 빌드 조건과 대표 입력 규모를 정하고, 같은 조건에서 반복해서 측정할 계획을 세울 수 있습니다. 필요한 응답 속도는 프로그램의 목적에 따라 달라지므로, 이 수업에서 특정 시간 제한을 정답으로 정하지는 않습니다. 또한 처리 속도가 빠르더라도 검색 결과가 틀리면 요구사항을 충족한 것이 아닙니다.

연습 4 해설

예를 들어 “나는 게임의 자원 목록 도구를 만들고 싶다. 특히 필요 없는 자료가 메모리에 계속 남는 문제를 이해해야 한다. 그래서 C++에서 객체의 수명과 소유권을 배우려 한다”라고 작성할 수 있습니다. 다른 답도 가능합니다. 중요한 것은 프로젝트의 제약과 배우려는 개념이 연결되어 있는가입니다. C++이면 언제나 가장 빠르다거나 AI는 C++ 코드를 작성하지 못한다는 주장을 이유로 삼지는 않습니다.

연습 1을 바탕으로 한 네 줄 메모 예시

  1. 이름에 검색어가 포함된 모든 항목을 원래 순서로 반환한다.

  2. 제시된 결과에는 강철검이 빠져 있다. 빈 목록 처리와 큰 입력의 비용은 아직 확인하지 않았다.

  3. 빈 목록에서는 빈 결과를, [나무검, 강철검, 회복약]과 “검”에서는 [나무검, 강철검]을, [회복약]과 “검”에서는 빈 목록을 예상한다.

  4. 항목 누락을 수정한 뒤 기능 결과를 다시 비교하고, 목표 환경과 자료 규모에서 정한 응답 조건을 만족하는지 측정한다.

위 메모는 검증 계획이며, 테스트를 통과했다는 보고가 아닙니다. 아직 실행하지 않았다면 확인할 내용을 계획으로 적고, 실제로 확인한 사실과 구분해야 합니다.

8 다음 수업으로

이번 수업에서는 원하는 동작을 정하고, 그 동작을 확인할 근거를 남기는 과정을 살펴보았습니다. 코드가 어디에서 왔는지와 관계없이 필요한 과정입니다. 이후에는 이 판단을 데이터 처리 비용, 객체의 수명과 외부 코드의 사용 조건까지 넓혀 가겠습니다.

다음 수업인 00-2에서는 개발 환경을 준비하고 작은 프로그램을 직접 빌드하고 실행하겠습니다. 실행 전의 예상과 실제 결과를 비교하면서 확인하는 과정을 연습합니다. 이번에 작성한 네 줄 검토 메모도 이후 실습에서 계속 활용할 수 있습니다.
